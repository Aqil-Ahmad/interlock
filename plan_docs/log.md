## 2026-08-22

- **Fixed:** worktree filtering depended on a porcelain detail. On git 2.39 a locked worktree whose directory is gone prints `locked` and not `prunable`, which is what the code assumed — but whether `worktree list` annotates both has moved between versions, and CI runs 2.55. The filter now skips a worktree that is prunable **and not locked**, which is correct under either behaviour and matches what `worktree prune` actually does. The asymmetry is deliberate: an unlocked missing worktree is garbage awaiting pruning and holds no observable work, a locked one is state someone chose to keep and merely cannot be reached, so it is unknown.
- **Fixed:** `matchesGlob` tested a literal match before `*`, so a name containing a literal `*` could consume the wildcard meant to span it — `*?` against `*` answered false. Refnames forbid `*` and `?` so it was unreachable, but the matcher is now correct standalone. 28 cases pass, including the greedy-overshoot and give-back cases a scanning matcher usually fails.
- **Deferred with a reason:** a per-`status` timeout shorter than the runner's default. Discovery reads worktrees serially, so an unreachable-but-not-absent worktree burns the full timeout before returning unknown. Picking a bound without the watcher's latency numbers would trade that for reporting a slow but working worktree as unreadable, which is the worse error. Recorded in the watcher task, where the numbers get measured.
- **Removed:** the `init -b main` unborn-HEAD test. An unborn HEAD resolves symbolically, so that fixture cannot tell correct behaviour from a hardcoded `main`; the `trunk` variant beside it can.

- **Reviewed the rest of M1 against what the runner and discovery now do.** Six tasks moved. Dirty-state snapshots: the recipe was checked end to end through the hardened runner first — seed, scoped `add`, `write-tree`, ignored file excluded, user index byte-identical — so the task stands, with the `indexFile` rules the guard now enforces written into it. SQLite store and `interlock status`: `dirty` is three-valued now, and a schema or a display that folds unknown into clean loses the distinction for good. Watcher: a worktree with no dirty state has no OID to deduplicate against. ChangeSet extraction: `--numstat` and `--name-status` are computed internally and safe, but a patch-producing diff runs the repository's `diff.external` and `textconv` drivers, so those need `--no-ext-diff --no-textconv` — measured both ways. User-repo-untouched: hash the git dir a linked worktree shares, and make the cycle include a snapshot so the index-only path is covered rather than skipped.
- **Unchanged:** repo config override, daemon skeleton, agent session hooks, and the single-git-call-site test. Nothing this session touched what they depend on.

- **Fixed, and the previous fix was wrong:** collapsing runs of `*` stopped `****x` from backtracking and did nothing for the pattern class that matters. `a*a*a…b` against a name of `a`s is exponential in the number of wildcards, not their adjacency: 20 seconds at a 33-character pattern, and the 200-character cap allows 99 of them. The test shipped last round aimed at the adjacent case, so a live denial of service sat behind a green assertion — the worst state a security control can be in. `matchesGlob` no longer builds a regex at all; it scans with a single backtrack point, bounded by the product of the two lengths. The reviewer's 198-character pattern now takes 0 ms, and the test covers both classes.
- **Decided:** `BranchRef.dirty` is nullable, and `null` means the worktree could not be read. A worktree marked with `git worktree lock` — which is what a worktree on a removable volume is locked for — keeps its listing when its directory disappears, so it carries `locked` rather than `prunable` and reaches `status`, which exits 128. Failing there took down discovery for every branch in the repository, and reporting it clean would have been worse. Making the field nullable put the choice in the type: `contentIdentity` now returns `null` for an unobserved worktree rather than the head alone, which would have let a result computed from a clean tree be reused for a tree nobody read.
- **Fixed:** `parseStatus` consumed the source field of a rename, and nothing tested it. Removing that line still passed all 22 tests while producing the garbage path `xt` in both file lists, from `a.txt` read as a status entry.
- **Fixed:** `discovery` had its own weaker `verbOf` beside the runner's correct `subcommandOf`, which skips global-flag values. Not reachable — every call site here leads with the verb, and the runner refuses reserved global flags — but two implementations of one idea in one package is how the wrong one gets copied. `subcommandOf` is exported and shared.
- **Corrected:** the default-branch comment claimed `main` was the fallback for an unborn HEAD. An unborn HEAD still resolves symbolically, so a repository initialised on `trunk` reports `trunk`; the literal `main` is reached only by a detached HEAD with no `origin`. Both paths are now tested, and the `origin`-only limitation is stated where it is decided.
- **Removed:** `WorktreeEntry.head`, parsed and stored and never read — `headSha` comes from `for-each-ref`.

- **Fixed:** `matchesGlob` translated every `*` to its own `.*`, so adjacent wildcards backtracked exponentially — measured 157 ms at ten stars, 25.5 s at sixteen, against a sixteen-character branch name. Ignore patterns come from the repository's own config, which the watched agents write, so a checked-in file could stall the discovery loop for as long as its author liked. Runs of `*` now collapse to one wildcard; the same pattern takes 1 ms.
- **Fixed:** `?` was missing from the escape set and survived into the regex as a quantifier, so `wip?` kept `wipe` and dropped `wip` — the exact inverse of the glob. It now means one character.
- **Fixed:** `mergeBase` returned `null` for any non-zero exit. git exits 1 for refs with no common ancestor and 128 for a ref it cannot resolve, so a typo or a stale ref reported as "not comparable" and the pair was dropped from analysis in silence. Only exit 1 is an answer now.
- **Decided:** a repository has one identity, and it is the main worktree's path. `--show-toplevel` answers with the worktree the path sits in, so opening the same repository through a linked worktree produced a second `Repo` row and a second shadow clone — on M1's main path, whose exit criterion is three worktrees under active edit. git lists the main worktree first from anywhere in the repository, which is the one path every worktree agrees on. The alternative, keying identity on `--git-common-dir` and carrying the worktree separately, would change the handle type and the store schema for no gain here.
- **Fixed:** `required()` put raw git stderr in `remedy`. stderr names branches and paths, `details` is documented as carrying neither secrets nor file contents, and an `InterlockError` reaches the API and the agents — so the diagnostic is gone from the error and the remedy says what to do. The runner already logs the failing command through the redacting sink.
- **Fixed:** `dataDir` was optional, so `describeRepo` without one produced a shadow path at the filesystem root. It is required by the type that needs it rather than checked at runtime.
- **Fixed:** an unmerged path has both status columns non-blank, so it was reported as staged and unstaged at once. It counts once, as unstaged.
- **Fixed:** `readDirtyState` ignored the exit code, so a failed `status` read as a clean worktree. Unreachable through `listBranchRefs` today — git marks an unreadable worktree prunable and it is dropped first, and an unreadable subdirectory only produces a warning with exit 0 — so the fix is unpinned by a test. Kept anyway: "clean" is the most dangerous wrong answer this function can give.
- **Rejected:** hardcoding `main` as the last-resort default branch and `origin` as the remote consulted. Both are documented fallbacks for a repository that declares nothing, not guesses that override what a repository does declare. Multiple remotes are a real limitation, and the day one matters is the day the config override lands.

## 2026-08-20

- **Fixed:** `isWithin` tested for a `..` prefix, so `relative()` returning `..bak` for a sibling _inside_ the directory read as an escape from it. An `indexFile` at `<repo>/..bak` passed the protection check and git would have written a stray file into the user's worktree. The escape has to be a whole `..` segment.
- **Fixed:** the runner never wrote to the child but left its stdin open, so `hash-object --stdin` and `update-index --stdin` blocked until the 30s timeout killed them — measured at 30,065 ms with the fix removed, 8 ms with it. The child now gets EOF immediately.
- **Decided:** a refusal is `GIT_COMMAND_REFUSED`, separate from `GIT_COMMAND_FAILED`. Both were one code distinguished only by `infra`, and the two mean different things to whoever is paged: a failure is the environment, a refusal is Interlock asking for something the safety rules forbid, which is a bug here.
- **Fixed:** the inherited-`GIT_*` filter compared case-sensitively. Windows matches variable names case-insensitively, so `git_dir` reaches git as `GIT_DIR`; the comparison is now case-insensitive on every platform.
- **Checked, no change:** an external `SIGTERM` is not misreported as a timeout. Node sets `error.killed` only when it issued the kill itself — measured `killed=false, signal=SIGTERM` for a signal sent by another process — so the `killed && SIGTERM` test already separates the two.

- **Fixed:** four ways the guard classified a write as safe, each verified against a real repo before and after. `read-tree -u` was `index-only` and overwrote an uncommitted edit — `-u` updates the working tree, which redirecting the index does not protect. `read-tree --index-output=<path>` was `index-only` and rewrote `.git/index`, because it overrides `GIT_INDEX_FILE` and so ignores the path the runner validated. `update-index --split-index` was `index-only` and left a `sharedindex.*` file in the user's `.git`, which lands in `$GIT_DIR` whatever the redirection says. `symbolic-ref -d <name>` was `read-only` and deleted the ref, because the positional-count heuristic sees the same one operand the reading form takes.
- **Decided:** flags are an **allowlist per verb**, not a list of dangerous ones. The first attempt at the fix was a denylist of the flags above, and it failed open within an hour of being written: git resolves any unambiguous prefix, so `--index-out=`, `--index=` and `--i=` are all `--index-output=`, and `--d` is `--delete` — all four verified rewriting the index or deleting a ref against real git while the guard called them safe. A denylist of flags fails exactly as the denylist of verbs did, and `--split-index` was found only by enumerating what each verb accepts. Long flags now match by prefix, which is safe only because git resolves a prefix to a flag it prefixes or to nothing; short flags match per character because git bundles them (`-um` is `-u`); scanning stops at `--` so a file named `-u` stays a path. Keyed by verb, since `-u` on `add` is `--update` and harmless while `-u` on `read-tree` writes the worktree.
- **Added:** a test that reads `git <verb> -h` and asserts every flag in the allowlist really exists. The prefix-matching argument holds only while each listed name is a real flag — an invented one licenses abbreviations of whatever else shares its prefix — and `read-tree --update`, which the first fix listed, turned out not to be a git flag at all.
- **Fixed:** `indexFile` validation compared normalised paths, which is not where a write lands. A symlink pointing at `.git` passed the check and rewrote the user's index, and so did an ordinary macOS path alias — `tmpdir()` returns `/var/folders/...` for a directory whose real path is `/private/var/folders/...`, so a handle and an `indexFile` could name the same file and compare as different. Both sides now resolve through `realpath`, the target via its parent since git has not created it yet, and an unresolvable path is refused rather than assumed external.
- **Decided:** flag checking covers the four verbs where a flag decides the class, not every flag of every allowed verb. `diff --output=<path>` writes a file and `grep -O` runs a program, but argv is built by Interlock and never supplied by a repository; the guard exists for a `kind` that did not survive a `JSON.parse`, not for attacker-chosen arguments. Recorded where the allowlist is defined so the boundary is deliberate.
- **Corrected:** `maxBufferBytes` counts bytes, not decoded characters. Measured on Node 26 — eight two-byte characters trip a limit of ten — because `execFile` measures with `Buffer.byteLength` when an encoding is set. The previous note claimed the opposite; the name was right and the comment was wrong.
- **Moved:** the index-redirection tests that used fictional paths. The guard now touches the filesystem, so only the cases decided on a path's shape stay unit tests and the rest run against a real repository.
- **Fixed:** an index redirection was checked against `rootPath` and `gitDir` only, which misses the git directory a linked worktree shares. A worktree's git dir is `<main>/.git/worktrees/<name>`, so its handle names neither the main checkout nor `<main>/.git`, and the index a redirection must miss lives in both. Branches under active edit sit in linked worktrees here, so this is the ordinary case.

- **Decided (ADR-0005):** per-pair worktree pool replaces the single shared scratch worktree decided on 08-12. Small LRU pool, default 4, entered only after the overlap filter. Each check updates a slot by delta — `merge-tree --write-tree` → `commit-tree` → `reset --hard` — instead of extracting the tree, which turns the measured 1.62 s into the size of the change. `.tsbuildinfo` persists per slot; eviction is expensive and the scheduler must prefer hot pairs over rotating new ones.
- **Decided:** M3 hosts the TypeScript LanguageService in-process, one per hot pair, rooted at its pool slot — justified by the 436 ms spawn floor against 350 ms of real incremental work. **Caveat found while writing it up:** tsconfig `plugins` are loaded and executed by the language-service host, and the tsconfig comes from an agent-written merged tree, so plugins must be stripped from the resolved config or the daemon executes repository code and breaks hard rule 2 in the one place the sandbox does not cover.

- **Verified:** ADR-0005's load-bearing assumption holds. TypeScript keys `.tsbuildinfo` on content, not mtime — rewriting every source file with identical bytes costs 439 ms against 437 ms untouched and 1036 ms cold. A `reset --hard` therefore invalidates only genuinely changed files, which is what makes the pool's delta update worth doing.

- **Verified:** symlinked `node_modules` satisfies `tsc` from a tree at a different path — root and per-package links, clean build, correct emit. ADR-0005's other load-bearing assumption holds. The pool must invoke `node_modules/.bin/tsc` directly and never shell through a package manager.

- **Measured (the missing number):** typecheck cost on openselfservice — 85,224 lines of TypeScript across a 39-package turbo monorepo, npm workspaces. Medians.
  - `git merge-tree --write-tree`: **12.1 ms**, against archestra's 12.8 ms on a repo 9× larger. Merge cost is effectively constant — it tracks the diff, not the repository.
  - Materialise merged tree: **590 ms** (58 MB, 2,131 files), against archestra's 1.62 s (276 MB). Scales with tree size, sub-linearly.
  - Full cold build: **88.8 s** (38 of 39 packages; the Next.js app failed on skipped native install scripts).
  - Warm build, nothing changed: **1.85 s** — all cache hits.
  - **Warm build, one file changed in a mid-graph package: 12.28 s.** This is the realistic per-check cost.
  - Raw `tsc` once internal dependencies are built: 0.94 s for a 4.3k-line workspace, 2.31 s for an 11.3k-line one.
- **Found — this changes M3:** in a monorepo you cannot typecheck a merged tree by running `tsc`. Raw `tsc` fails with `TS2307: Cannot find module '@o2s/utils.logger'` because internal workspace packages resolve through their `dist/`, which does not exist until they are built. The semantic check is therefore "build the internal dependency graph, then typecheck" — 12.28 s incrementally, not the 0.94 s the compiler alone suggests. M3's toolchain detection has to discover and run the build orchestrator, not just find the typechecker.
- **Implication:** 12.28 s per check sits comfortably inside the stated 3-minute budget for a typecheck finding, but four hot pooled pairs is roughly 50 s of CPU per round, so pool size and check frequency are now tunable against a real number rather than a guess. Cold is 88.8 s here and would be far worse on a repo the size of archestra, which is the whole argument for the pool.
- **Design consequence:** the pool slot must persist the **build orchestrator's cache** as well as `.tsbuildinfo` — turbo's `.turbo` directory was 54 MB here, and losing it is the difference between 1.85 s and 88.8 s. Add it to ADR-0005's list of state that eviction destroys, and count it in the disk quota.

## 2026-08-12

- **Decided:** merges use `git merge-tree --write-tree` in the shadow object database, not a worktree per pair. Merged trees materialise into one reusable scratch worktree with `node_modules` symlinked from the user's checkout; a `package.json` or lockfile change routes that pair to a slow install path.
- **Decided:** `merge-tree` solves merge cost; the scheduler solves typecheck cost, and typecheck cost is the budget that matters. A semantic conflict is a merge that came out clean, so the merge step never filters those out — overlap does.
- **Decided:** the TypeScript compiler is the semantic detector. M3 gains a baseline differ (report only diagnostics absent from base, A and B alone) and an attribution engine (which branch caused which half). The hand-built rename and signature matchers are dropped.
